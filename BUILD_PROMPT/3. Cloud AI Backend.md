You are a senior cloud backend engineer and ML systems architect.

Design and implement the complete cloud AI backend for Quicknitch — a consumer flying AI
companion device with millions of users.

Stack requirements:
- Cloud provider: AWS (primary), with GCP fallback for AI inference
- Infrastructure as code: Terraform
- Container orchestration: EKS (Kubernetes)
- Languages: Python 3.11 (AI services), Go 1.21 (real-time gateway), TypeScript (API layer)
- AI models: OpenAI GPT-4o API (primary LLM), Whisper API (STT),
  ElevenLabs API (TTS), with self-hosted fallback using Ollama + Llama 3.1 70B

Implement the following services:

1. REAL-TIME VOICE GATEWAY (Go service)
   - WebSocket server handling 100K concurrent device connections
   - Protocol: devices connect via wss://voice.quicknitch.ai/v1/stream
   - Message framing: binary frames, first 4 bytes = frame type + length
   - Frame types: AUDIO_CHUNK (Opus 32kbps), AUDIO_END, RESPONSE_AUDIO,
     HEARTBEAT, ERROR, SESSION_INIT
   - Session init payload: {device_id, user_id, session_token, firmware_version}
   - On AUDIO_CHUNK: buffer in Redis stream until AUDIO_END received,
     then publish to Kafka topic "voice_requests"
   - On RESPONSE_AUDIO: stream TTS audio chunks back to device in 100ms segments
   - Horizontal scaling: stateless, sticky sessions via AWS NLB with connection draining
   - Implement connection rate limiting: 10 new connections/second per IP
   - Full Prometheus metrics: connections_active, messages_per_second,
     audio_bytes_received, latency_p50/p95/p99

2. VOICE PROCESSING PIPELINE (Python service)
   - Kafka consumer on "voice_requests" topic
   - Processing steps:
     a. Retrieve user profile + memory context from DynamoDB
     b. Run Whisper STT on buffered audio (async HTTP to OpenAI API)
     c. Build LLM prompt with: system prompt + last 5 memory excerpts (RAG)
        + current transcript
     d. Stream GPT-4o response via OpenAI streaming API
     e. Pipe LLM text chunks to ElevenLabs streaming TTS API
     f. Forward TTS audio chunks to voice gateway via Redis pub/sub
     g. Store conversation transcript asynchronously to DynamoDB
     h. Trigger memory extraction job (see Memory Service)
   - Full error handling: STT failure → retry once → fallback to local Whisper
   - LLM timeout (>8s) → send "Let me think about that" audio stall message
   - Target end-to-end latency: <1.2 seconds from AUDIO_END to first audio byte

3. MEMORY AND PERSONALIZATION SERVICE (Python)
   - Memory schema in DynamoDB:
     {user_id, memory_id, timestamp, category, content_embedding (1536-dim),
      content_text, importance_score, access_count, last_accessed}
   - Categories: preference, event, habit, person, location, task
   - Memory extraction: after each conversation, run GPT-4o-mini with prompt:
     "Extract 0-3 key facts worth remembering from this conversation.
      Return JSON array: [{category, content, importance (1-10)}]"
   - Store extracted memories with OpenAI text-embedding-3-small embeddings
   - RAG retrieval: on each new query, embed the query, search DynamoDB
     via cosine similarity (using auxiliary FAISS index in ElastiCache),
     return top 5 memories above threshold 0.72
   - Memory decay: importance_score -= 0.1 per week if not accessed
   - Memory limit: 10,000 memories per user (free), unlimited (Plus)
   - Memory export API: GET /v1/memory/export → returns full JSON dump
   - Memory delete API: DELETE /v1/memory/{memory_id} or DELETE /v1/memory/all

4. DEVICE MANAGEMENT SERVICE (TypeScript + AWS IoT Core)
   - Device registration: POST /v1/devices/register
     {device_serial, firmware_version, hardware_revision}
     Returns: device_id, IoT certificate, private key, IoT endpoint
   - MQTT topic structure:
     quicknitch/{device_id}/telemetry (device → cloud, QoS 0)
     quicknitch/{device_id}/commands (cloud → device, QoS 1)
     quicknitch/{device_id}/ota (cloud → device, firmware update chunks)
   - Telemetry ingest: battery_level, flight_time_seconds, error_codes,
     firmware_version, wifi_rssi — stored to TimescaleDB on RDS
   - OTA update flow:
     a. Admin uploads new firmware binary to S3
     b. Create OTA job targeting device cohort (by firmware_version or device_id list)
     c. Device receives MQTT message with S3 presigned URL
     d. Device downloads in 4KB chunks, verifies SHA256, reboots
     e. Device reports new firmware_version on next telemetry

5. AUTHENTICATION AND USER SERVICE (TypeScript)
   - Auth: Auth0 (social login + email/password), JWT tokens, refresh token rotation
   - User profile: {user_id, email, plan (free/plus/family), created_at,
     voice_id (ElevenLabs), personality_settings, privacy_zones[]}
   - Device pairing: QR code scan in app → app sends pairing_token to backend
     → backend validates device serial + generates long-lived device_token
   - Family plan: up to 4 user_ids linked to one subscription,
     each with separate memory and voice profile
   - Stripe integration for subscription billing:
     POST /v1/billing/subscribe {plan, payment_method_id}
     Webhook handler for subscription events (created, canceled, past_due)

6. INFRASTRUCTURE (Terraform)
   Write complete Terraform for:
   - VPC with public/private subnets across 3 AZs
   - EKS cluster (managed node groups: t3.medium for API, c5.2xlarge for AI pipeline)
   - ElastiCache Redis cluster (3 nodes, r6g.large) for session state + pub/sub
   - MSK Kafka cluster (3 brokers, kafka.m5.large) for voice request queue
   - DynamoDB tables with GSIs for memory service
   - RDS TimescaleDB (db.r6g.large, Multi-AZ) for telemetry
   - S3 buckets: firmware-releases, user-video-clips, conversation-transcripts
   - CloudFront distribution for static assets + firmware downloads
   - AWS IoT Core with certificate authority setup
   - Route53 DNS + ACM certificates
   - Auto-scaling policies: voice gateway scales at 70% CPU,
     AI pipeline scales at queue depth > 100 messages

   - PagerDuty alerts: error_rate > 1%, p99_latency > 3s, kafka_lag > 500
